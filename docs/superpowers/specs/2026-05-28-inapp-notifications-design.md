# In-App Employee Notification System — Design Spec

> **Status:** Approved for implementation  
> **Date:** 2026-05-28  
> **Scope:** Maliev.Intranet only

---

## Problem

When a customer accepts a quote, `ProjectService` publishes `ProjectQuotationAcceptedEvent` but no component in the Intranet consumes it. Employees have no real-time signal that production planning is required. If they miss the status change on the project list, the job sits unplanned — risking late delivery.

---

## Goal

Deliver a persistent, per-employee in-app notification that appears in the Intranet TopBar the moment a quote is accepted. Employees who are away from their desk see the badge when they return. Clicking navigates directly to the project's Production Plan tab.

---

## Constraints

- **No email.** In-app only.
- **Per-employee.** Each employee has independent read state. Reading a notification for one employee does not affect any other.
- **Persistent across page refreshes and BFF restarts.** Stored in the existing `IntranetDbContext` PostgreSQL database.
- **All employees** receive every quote-accepted notification.
- **Real-time.** New alerts appear via SignalR without requiring a page refresh.

---

## Architecture

### Data flow

```
ProjectService.AcceptQuotationAsync()
  └─ publishes ProjectQuotationAcceptedEvent (MassTransit)

Intranet BFF — ProjectQuotationAcceptedConsumer
  ├─ inserts 1 row into alert_notifications (IntranetDbContext / PostgreSQL)
  └─ hub.Clients.All.SendAsync("ReceiveAlert", AlertSignalRPayload)

Blazor WASM Client
  MainLayout (owns HubConnection)
    └─ On("ReceiveAlert") → AlertService.AddAlert(alert)

  AlertService (scoped singleton, registered in DI)
    ├─ OnInitialized: GET /api/v1/alerts → populate from DB
    ├─ AddAlert()   → prepends to in-memory list, fires Changed
    ├─ MarkRead()   → POST /api/v1/alerts/{id}/read, removes from list
    ├─ MarkAllRead() → POST /api/v1/alerts/read-all, clears list
    └─ event Changed → subscribers call StateHasChanged

  NotificationBell (new Razor component, placed in TopBar)
    ├─ subscribes to AlertService.Changed
    ├─ bell icon + red badge (unread count)
    ├─ toggle dropdown panel on click
    ├─ close panel on navigation (LocationChanged)
    └─ item click → AlertService.MarkRead(id) + NavigateTo production-plan tab
```

### API endpoints (all authenticated, require employee session)

| Method | Path | Purpose |
|--------|------|---------|
| GET | `/api/v1/alerts` | Return unread alerts for this employee (no receipt row) |
| POST | `/api/v1/alerts/{id}/read` | Insert receipt for this employee |
| POST | `/api/v1/alerts/read-all` | Insert receipts for all non-expired alerts for this employee |

Employee identity: `User.FindFirst(ClaimTypes.NameIdentifier)` — same claim used throughout the BFF.

## Data Model

### `alert_notifications` table

| Column | Type | Notes |
|--------|------|-------|
| `id` | UUID PK | Generated by consumer |
| `type` | VARCHAR(64) | `"QuoteAccepted"` |
| `project_id` | UUID | From event payload |
| `project_number` | VARCHAR(32) | e.g. `PRJ-2026-0027` |
| `customer_name` | VARCHAR(256) | From event payload |
| `part_count` | INT | Count of active parts |
| `process_types` | VARCHAR(256) | Comma-separated, e.g. `"CNC, FDM"` |
| `occurred_at_utc` | TIMESTAMPTZ | When the event arrived |
| `expires_at_utc` | TIMESTAMPTZ | `occurred_at_utc + 7 days` |

Index on `expires_at_utc` for efficient expiry filtering.

### `alert_read_receipts` table

| Column | Type | Notes |
|--------|------|-------|
| `notification_id` | UUID FK → alert_notifications | Cascade delete |
| `employee_id` | VARCHAR(128) | From NameIdentifier claim |
| `read_at_utc` | TIMESTAMPTZ | When the employee read it |

Primary key: `(notification_id, employee_id)`.

### Unread query

```sql
SELECT n.*
FROM alert_notifications n
LEFT JOIN alert_read_receipts r
  ON r.notification_id = n.id AND r.employee_id = @employeeId
WHERE r.notification_id IS NULL
  AND n.expires_at_utc > NOW()
ORDER BY n.occurred_at_utc DESC
LIMIT 50
```

## Frontend Components

### New files

**`Maliev.Intranet.Client/Services/AlertService.cs`**  
Scoped singleton. Holds `List<AlertSummary>` in memory.

```csharp
public class AlertService
{
    public IReadOnlyList<AlertSummary> Alerts { get; }
    public int UnreadCount { get; }
    public event EventHandler? Changed;

    public Task InitializeAsync();          // called once from MainLayout
    public void AddAlert(AlertSummary a);   // called from SignalR handler
    public Task MarkReadAsync(Guid id);     // POST + remove from list
    public Task MarkAllReadAsync();         // POST + clear list
}
```

**`Maliev.Intranet.Client/Components/NotificationBell.razor`**  
- Subscribes to `AlertService.Changed`
- Bell icon (`Icons.Material.Outlined.Notifications`) + red MudBadge
- Click toggles `_panelOpen`
- Dropdown panel: list of `AlertSummary`, "Mark all as read" button, footer link
- Each row: project number + link, customer, part count + process types, age (relative time)
- Row click: `AlertService.MarkReadAsync(id)` then `Navigation.NavigateTo($"/projects/{projectId}?tab=production-plan")`
- Close on `Navigation.LocationChanged`
- Implements `IDisposable` (unsubscribe from Changed + LocationChanged)

**`Maliev.Intranet.Client/Shared/AlertSummary.cs`** (or in Shared project)  
DTO: `Id`, `ProjectId`, `ProjectNumber`, `CustomerName`, `PartCount`, `ProcessTypes`, `OccurredAtUtc`.

## Error Handling

| Scenario | Behaviour |
|----------|-----------|
| Consumer DB write fails | Log error, do not rethrow — MassTransit will retry; project status change is unaffected |
| SignalR broadcast fails | Log warning, swallow — clients will still load alerts from DB on next page load |
| `GET /api/v1/alerts` fails on client load | Show empty panel, no badge — app remains functional |
| `POST read` fails | Keep alert in local list (stays unread) — safe failure, no data loss |
| Alert already read (duplicate POST) | `INSERT ... ON CONFLICT DO NOTHING` (or EF Core `ExecuteUpdateAsync` with upsert) |

## Expiry

Alerts expire after **7 days** (`expires_at_utc = occurred_at_utc + 7 days`). Expired alerts are excluded from all queries. No background cleanup job is needed in this phase — expired rows are filtered in SQL and do not affect correctness. A periodic cleanup can be added later if table growth becomes a concern.
